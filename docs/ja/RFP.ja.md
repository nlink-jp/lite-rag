# 提案依頼書（RFP）: CLI ベース RAG ドキュメント検索システム

## 1. はじめに

本書は、CLI ベースのドキュメント検索・質問応答システムの開発要件を定義するものである。本システムの中核は検索拡張生成（RAG）アーキテクチャであり、OpenAI 互換 API エンドポイント経由でアクセスするローカル大規模言語モデル（LLM）を活用する。

主たる目的は、Markdown ドキュメント群から情報を検索し統合するための、ポータブルかつ効率的で強力なツールを作ることである。

## 2. プロジェクト概要

提案するシステムはコマンドラインアプリケーションであり、利用者は以下を行える。
1.  Markdown ドキュメント群を **インデックス化** し、検索可能なベクトルデータベースを構築する。
2.  インデックス済みドキュメントに自然言語で **問い合わせ** し、LLM が生成した簡潔で文脈を踏まえた回答を得る。

主インターフェースは CLI だが、将来的に他のフロントエンドのバックエンドとして機能しうる設計とすること。

## 3. 要件

### 3.1. 機能要件

-   **インデックス化（`index` コマンド）:**
    -   Markdown ファイルを格納したディレクトリのパスを受け取る。
    -   ドキュメントを解析し、意味のあるセマンティックチャンクに分割する。
    -   指定された埋め込みモデルを用いて各チャンクのベクトル埋め込みを生成する。
    -   チャンクと対応するベクトルを DuckDB データベースに保存する。
    -   インデックス処理は冪等であり、新規または変更されたドキュメントでデータベースを更新するために再実行できること。

-   **質問応答（`ask` コマンド）:**
    -   利用者から自然言語の質問を受け取る。
    -   質問に対する埋め込みを生成する。
    -   DuckDB でベクトル類似度検索を行い、最も関連性の高いドキュメントチャンクを取得する。
    -   利用者の質問と取得した文脈を組み合わせ、チャット LLM 向けのプロンプトを構築する。
    -   プロンプトを LLM に送信し、生成された回答を利用者のターミナルへストリーミングで返す。

### 3.2. 技術スタック

-   **プログラミング言語:** Go
-   **データベース:** DuckDB（リレーショナルデータとベクトルの保存・検索の双方に使用）
-   **LLM バックエンド:** LM Studio（ローカルサーバー、OpenAI API 互換）
-   **埋め込みモデル:** `nomic-ai/nomic-embed-text-v1.5-GGUF`
-   **チャットモデル:** `openai/gpt-oss-20b`（利用者の環境に設定済みで利用可能）
-   **CLI フレームワーク:** `cobra` のような標準的な Go ライブラリを推奨。

### 3.3. 非機能要件

-   **ポータビリティ:** 最終的な実行ファイルは `linux/amd64`、`linux/arm64`、`darwin/arm64` 向けにクロスコンパイルすること。組織のリリースアーカイブ標準に従い darwin は arm64 のみ（Intel 非対応）。Windows は DuckDB バインディングが cgo を必要とするためスコープ外。
-   **パフォーマンス:** 一般的なドキュメントセットに対して、インデックス化とクエリ応答の時間が十分に高速であること。
-   **設定:** API エンドポイント、モデル名、データベースパスといった設定について、外部設定（`config.toml` のようなファイルまたは環境変数）をサポートしなければならない。
-   **保守性:** コードベースは `RULES.md` に定義されたルールを遵守し、明確さ・テスト容易性・関心の分離を促進すること。

## 4. 既知の問題と課題

初期セットアップ段階で、Go モジュールの依存関係に関する重大な課題が発生した。

-   **問題:** `go mod tidy` および `go get` コマンドがモジュール（`github.com/duckdb/go-duckdb`）のダウンロードに失敗し、"Repository not found" エラーを報告した。
-   **根本原因の分析:** この問題は、開発環境のセキュリティサンドボックス（macOS Seatbelt）が、Go のツールチェーンが内部的に呼び出す `git` プロセスのネットワークアクセスを遮断していたことに起因する。
-   **試行した緩和策:**
    1.  `GOPATH` と `GOMODCACHE` をプロジェクトローカルに設定する。
    2.  `GOPROXY` を用いてモジュールのダウンロードを HTTPS 経由に強制する。
-   **結果:** Go ツールチェーンがモジュールバージョンの解決のために直接 `git` 呼び出しにフォールバックし続けたため、これらの試みは失敗した。利用者がサンドボックスを無効化したと報告した後も問題は解消せず、環境または設定に起因する複雑な問題である可能性が示された。

**本プロジェクトの重要な要件は、この制約された環境下で Go の依存関係を管理するための堅牢かつ確実な解決策を提案することである。**
